# Исследовательский стенд: three.js vs react-three-fiber

Стенд для воспроизводимого сравнения производительности двух подходов рендеринга 3D-сцен в браузере: императивный `three.js` и декларативный `react-three-fiber` (R3F).

## Структура монорепозитория

```
benchmark/
├── packages/
│   ├── scene-spec/        Платформо-независимые спецификации сцен (S1, S2, ...).
│   │                      ОБА приложения читают одну и ту же спецификацию,
│   │                      что гарантирует идентичность графического контента.
│   │
│   ├── metrics/           Сбор метрик: FPS, frame time, p1-low, heap, stddev.
│   │                      Подключается к requestAnimationFrame цикла рендера.
│   │
│   ├── impl-threejs/      Императивная реализация на чистом three.js.
│   │                      Vite + TypeScript, без React.
│   │
│   ├── impl-r3f/          Декларативная реализация на react-three-fiber.
│   │                      Vite + React + R3F.
│   │
│   └── harness/           Playwright-раннер: автоматизирует прогоны,
│                          собирает результаты, считает статистику.
```

### Ключевой принцип

`scene-spec` хранит описание сцены в виде структуры данных (число объектов, геометрии, материалы, освещение, параметры рендера). Обе реализации читают одинаковую спецификацию и строят сцену каждая своим способом. Это исключает расхождения в графическом контенте — сравниваются именно **способы управления**, а не сами сцены.

## Сценарии

| ID | Назначение | Гипотеза |
|----|-----------|----------|
| S1 | GPU-bound: тяжёлая статичная сцена | H1: FPS не различается |
| S2 | CPU-bound: частые обновления состояния | H2: R3F стабильнее при правильной архитектуре |
| S3 | Cold start: TTFR / TTI / bundle size | H3: R3F стартует медленнее |
| S4 | Input latency: реакция на ввод | — |
| S5 | Scale: точка деградации FPS | — |

Реализованы **S1, S2, S3, S4, S5**.

### S5 — Scale (точка деградации)

Та же CPU-bound анимированная сцена, что и в S2, прогоняется при возрастающем
числе объектов (`100, 500, 1000, 2000, 5000, 10000, 20000, 50000`).
`ScaleCollector` пишет FPS на каждом уровне и **останавливает свип**, как только
median FPS падает ниже порога (`--fpsFloor`, по умолчанию 30) — это и есть точка
деградации. Камера на каждом уровне кадрирует всё облако (формула общая для
обеих реализаций).

Цели сравнения: `threejs`, `r3f-ref` (`?mode=ref`), `r3f-state` (`?mode=state`).

Параметры (`warmup`/`record` трактуются **поуровнево**):
```bash
npm run bench:s5
npm run bench -w @bench/harness -- --scenario s5 --levels 100,1000,5000,20000 --fpsFloor 30
```

Метрики (`BenchScaleResult`): `degradation_count` (первый count с median FPS ниже
порога) и `fps_median_by_count` — кривая FPS по уровням.

### S4 — Input latency

Сцена из 2000 статичных объектов плотным облаком в кадре. `InputCollector`
сам синтезирует детерминированный (seeded) поток `pointerdown`-событий и
диспатчит их на canvas, измеряя задержку «pointerdown → отрисовка визуального
отклика» (emissive-подсветка объекта по raycast'у).

Raycasting (`three.Raycaster`) одинаков в обеих реализациях, поэтому в зачёт
идёт только стоимость **доставки** отклика до объекта:

| Цель | Путь доставки подсветки |
|------|-------------------------|
| `threejs` | императивно: `material.emissive` прямо на меше |
| `r3f-ref` (`?mode=ref`) | императивно через `ref`, минуя реконсиляцию |
| `r3f-state` (`?mode=state`) | `setState` → React-реконсиляция дерева (наивный путь) |

Метрики (`BenchInputResult`): `input_latency_ms_{avg,median,p95,p99,max,stddev}`,
`frames_to_feedback_avg`, доля попаданий raycast'а (`recorded_samples` /
`dispatched_clicks`).

## Запуск

```bash
# установка зависимостей
npm install

# запуск Three.js-реализации (http://localhost:5173)
npm run dev:threejs

# запуск R3F-реализации (http://localhost:5174)
npm run dev:r3f

# автоматический прогон S1 на обеих реализациях
npm run bench:s1

# прогон S4 (input latency): threejs vs r3f-ref vs r3f-state
npm run bench:s4

# прогон S5 (scale): свип по числу объектов до падения FPS < 30
npm run bench:s5
```

## Метрики (S1)

- **fps_avg** — среднее число кадров в секунду
- **fps_p1_low** — 1% худших кадров (стабильность)
- **frame_time_ms_avg** — среднее время кадра
- **frame_time_ms_stddev** — стандартное отклонение времени кадра
- **heap_mb** — пиковое использование JS heap

Каждый прогон: 5 сек прогрева + 30 сек записи. N=30 повторений на сценарий.

## Условия воспроизводимости

- Canvas: 1280×720, `devicePixelRatio = 1`
- Детерминированный PRNG для размещения объектов
- Прогрев перед записью метрик
- Идентичные модели, материалы, освещение, камера
