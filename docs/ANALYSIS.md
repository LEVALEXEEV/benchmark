# Обработка данных

Что и как считается из сырых замеров стенда: правила пилота (выбор числа
прогонов) и основного эксперимента (сравнение вариантов). Сырые данные и их
формат описаны в [DATA.md](DATA.md), порядок съёмки — в [MEASURE.md](MEASURE.md).

Статус правил:

- **раздел 3 (пилот)** — применены, реализованы в `analysis/pilot.ipynb`;
- **раздел 4 (основной эксперимент)** — предложение, утверждается до
  обработки кампании; открытые вопросы собраны в разделе 5.

---

## 1. Общие принципы

**1.1. Всё считается из сырых данных.** Стенд пишет только сырые замеры
(каждый кадр, каждый клик, отметки времени загрузки). Любое число в отчёте
получено кодом анализа из этих CSV — ничего не вписывается вручную и не
берётся из промежуточных итогов стенда.

**1.2. Единица анализа — прогон.** Прогон — одна загрузка страницы с одним
вариантом. Кадры и клики внутри прогона не являются независимыми
наблюдениями: соседние кадры похожи друг на друга (общий прогрев JIT,
состояние памяти, частота процессора в эти секунды). Если считать тысячи
кадров независимыми, разброс получится заниженным в десятки раз, и любая
мелкая разница покажется «значимой». Поэтому из каждого прогона берётся
**одно число — метрика прогона**, и статистика ведётся по прогонам.

**1.3. Ячейка.** Сочетание *платформа × сценарий × вариант × точка
нагрузки* (точка — только в S1). Например: «Mac · Chromium · S1 · r3f-ref ·
точка B». В ячейке — n прогонов, n значений метрики.

**1.4. Платформы не смешиваются.** Платформа — устройство и браузер
(«Mac · Chromium», «Windows · Firefox» …). Варианты сравниваются только
внутри одной платформы: там они снимались вперемешку, в одних и тех же
условиях. Между платформами сравниваются уже готовые результаты (раздел 4.9),
но не объединяются в одну выборку.

**1.5. Относительные величины, логарифмическая шкала.** Нас интересует
«во сколько раз» (R3F медленнее three.js на 8%), а не «на сколько
миллисекунд»: одна и та же разница в 1 мс значит много при кадре 4 мс и
мало при 40 мс. Поэтому метрики анализируются через натуральный логарифм:
отношение величин превращается в разность логарифмов, а разброс логарифма
(*s*) — это относительный разброс. Для малых значений *s* ≈ коэффициент
вариации: *s* = 0,03 означает «прогоны отличаются друг от друга примерно на
3%».

**1.6. Данные не исключаются по значению.** Выброс — не повод убрать
прогон: «странный» прогон тоже результат. Исключить можно только серию или
прогон по заранее известной причине, не зависящей от значения метрики
(серия не завершена, код не закоммичен — раздел 4.1). Стенд сам
останавливает серию при нарушении условий, поэтому таких случаев не
ожидается.

## 2. Метрика прогона: из чего и как считается

В этом разделе — как из CSV одного прогона получается одно число. Колонки
CSV описаны в [DATA.md](DATA.md).

### 2.1. S1 и S2 — плавность (строка CSV = кадр)

Берутся все кадры окна записи (30 с; прогрев 5 с в CSV не попадает).

| Метрика прогона | Формула | Роль |
|---|---|---|
| **среднее время кадра**, мс | среднее `frame_ms` по всем кадрам | главная |
| медиана времени кадра, мс | медиана `frame_ms` | дополнительная |
| p99 времени кадра, мс | 99-й перцентиль `frame_ms` (линейная интерполяция, как `numpy.percentile`) | дополнительная — «рывки» |
| FPS | 1000 / среднее время кадра | производная, для подписей |
| логика, мс | среднее `update_ms` | фаза — для объяснения |
| отрисовка на CPU, мс | среднее `render_ms` | фаза — для объяснения |
| вне фаз, мс | среднее (`frame_ms` − `update_ms` − `render_ms`) | фаза: работа между кадрами — коммиты React вне кадра, сборка мусора, ожидание |
| время GPU, мс | среднее `gpu_ms` по кадрам, где значение есть (только Chromium) | фаза — кто узкое место |

**Почему главная — среднее, а не медиана.** Среднее время кадра — это
пропускная способность: за 30 с прогона отрисовано 30 000 / среднее кадров.
Медиана говорит о «типичном» кадре, но у неё есть недостаток, найденный в
пилоте: если кадры чередуются (в Firefox вариант state даёт поровну кадров
по ≈ 18 и ≈ 66 мс), медиана может оказаться в любой точке между двумя
пиками, и от прогона к прогону «прыгает» на 40%. Среднее при этом стабильно
(разброс 1,5%). Подробно — `analysis/pilot.ipynb`, раздел 4.2.

**Как читать фазы.** Время кадра = логика + отрисовка на CPU + вне фаз.
Время GPU идёт параллельно с CPU: если GPU-время близко к времени кадра —
кадр ограничен видеокартой (так задуман S1); если намного меньше — кадр
ограничен процессором (S2).

### 2.2. S3 — холодный старт (одна строка CSV на прогон)

Все отметки — миллисекунды от начала открытия страницы.

| Метрика прогона | Формула | Роль |
|---|---|---|
| **время до первого кадра**, мс | `render_end_ms` | главная |
| загрузка кода, мс | `code_ready_ms` | этап |
| построение сцены, мс | `render_start_ms` − `code_ready_ms` | этап: создание WebGL, сцены, ожидание первого кадра |
| первая отрисовка, мс | `render_end_ms` − `render_start_ms` | этап |

Три этапа в сумме дают время до первого кадра. Размер сборки (КБ, сырой и
gzip) — свойство сборки, а не прогона: берётся из manifest серии и
приводится как есть, без статистики.

### 2.3. S4 — отклик на клик (строка CSV = клик)

Учитываются только клики с `outcome = ok` (клик попал в объект, отклик
отрисован). Доля промахов (`miss`) и прочих исходов приводится отдельно как
характеристика серии.

Для каждого клика:

| Величина клика | Формула |
|---|---|
| **задержка** | `render_end_ms` − `event_ms` — от создания события браузером до конца отрисовки кадра с откликом |
| очередь | `handler_start_ms` − `event_ms` — событие ждёт, пока страница его возьмёт |
| обработка события | `handler_end_ms` − `handler_start_ms` |
| обновление React | max(0, `applied_ms` − `handler_end_ms`) — если цвет поменялся уже внутри обработчика, фаза равна нулю |
| ожидание кадра | `render_start_ms` − max(`applied_ms`, `handler_end_ms`) |
| отрисовка | `render_end_ms` − `render_start_ms` |

Пять фаз в сумме точно дают задержку.

| Метрика прогона | Формула | Роль |
|---|---|---|
| **медиана задержки**, мс | медиана задержки по кликам `ok` прогона | главная |
| p95 задержки, мс | 95-й перцентиль | дополнительная |
| фазы, мс | медиана каждой фазы | для объяснения |

**Почему здесь медиана, а не среднее.** Клики приходят в случайный момент
кадра, поэтому задержка разбросана в пределах длительности кадра, а редкие
клики попадают на сборку мусора и дают выбросы в десятки мс. Медиана
описывает типичный отклик и не зависит от этих редких событий; редкие
события описывает p95.

### 2.4. S5 — масштабируемость (строка CSV = кадр уровня)

Прогон — свип: число объектов растёт по уровням 100, 141, 200, … (×√2),
на каждом уровне записывается не меньше 60 кадров.

1. Для каждого уровня: FPS уровня = 1000 / медиана `frame_ms` кадров уровня.
2. **Ёмкость при 60 FPS** — число объектов, при котором FPS опускается до 60.
   Между двумя соседними уровнями, где FPS переходит через 60 (первый ≥ 60,
   второй < 60), точка находится линейной интерполяцией в координатах
   (log N, log FPS) — на этих осях зависимость FPS от числа объектов почти
   прямая.
3. **Ёмкость при 30 FPS** — так же.

Обе ёмкости — главные метрики. Если FPS не пересёк порог в пределах
пройденных уровней (например, уже на первом уровне ниже 60), ёмкость для
этого прогона не определена — см. раздел 5, вопрос 4.

Медиана внутри уровня (а не среднее, как в S1/S2) здесь потому, что окно
уровня короткое (3 с), и разовая пауза на сборку мусора заметно сдвинула
бы среднее; чередования кадров у вариантов S5 (three.js, ref) нет.

## 3. Пилот: выбор числа прогонов

Реализовано в `analysis/pilot.ipynb`. Пилот — короткая серия (5 прогонов
на ячейку, в S3 — 10) на двух платформах: Mac · Chromium и
Windows · Firefox.

**Шаг 1. Допуск серий.** В расчёт идут серии, которые завершены, сняты на
закоммиченном коде и прошли проверку паритета сцен.

**Шаг 2. Метрика прогона** — по разделу 2, для главных метрик.

**Шаг 3. Разброс ячейки.** По *k* прогонам ячейки — стандартное
отклонение логарифма метрики *s* (относительный разброс между прогонами).

**Шаг 4. Поправка на малую выборку.** По 5 значениям разброс оценивается
неточно: истинный может быть заметно больше. Поэтому берётся верхняя
граница 80%-ного доверительного интервала разброса (Browne, 1995):

```
s↑ = s · √( (k − 1) / χ²(0,2; k − 1) )
```

При k = 5 это s × 1,56, при k = 10 — s × 1,29.

**Шаг 5. Число прогонов на вариант** — чтобы различить разницу δ между
двумя вариантами с уровнем значимости 5% и мощностью 80% (стандартная
формула объёма выборки для сравнения двух групп, на логарифмической шкале):

```
n = 2 · (1,96 + 0,84)² · s↑² / ln²(1 + δ)
```

δ — какую разницу нужно уметь различать: **5%** для времени кадра, времени
до первого кадра и ёмкости; **10%** для задержки ввода и хвостов (p99, p95) —
они по природе шумнее, и разница меньше 10% в них практически незначима.

Пример: s = 2% (s↑ = 3,1%) и δ = 5% → n = 2 · 7,85 · 0,031² / 0,0488² ≈ 7.

**Шаг 6. Двухуровневые ячейки.** Формула шага 5 предполагает, что значения
прогонов разбросаны вокруг одного уровня. Иногда прогоны ячейки делятся на
две устойчивые группы (в пилоте — Mac · Chromium · S2 · three.js: часть
прогонов ≈ 4,27 мс, часть ≈ 4,85 мс; уровень выбирается при старте процесса
браузера). Тогда *s* — это расстояние между группами, а не шум, и формула
теряет смысл. Ячейка считается двухуровневой, если, разделив
упорядоченные значения по наибольшему разрыву:

- в каждой группе не меньше 2 прогонов;
- разрыв больше 4 стандартных отклонений внутри групп;
- разрыв не меньше δ (более мелкие «ступеньки» при 5 прогонах — случайность).

**Шаг 7. Итог по сценарию.**

1. Максимум *n* по главным метрикам всех ячеек обеих платформ, кроме
   двухуровневых.
2. Не меньше **10**: формула опирается на нормальное приближение и при
   малых *n* занижает объём; бутстреп-интервалы основного анализа
   (раздел 4.3) при выборках меньше ≈ 10 ненадёжны.
3. Если в сценарии есть двухуровневая ячейка — не меньше **30**: для неё
   оценивается доля прогонов на каждом уровне, и при 30 прогонах ошибка
   доли не больше ±18 процентных пунктов.

**Результат:** S1 — 10, S2 — 30, S3 — 45, S4 — 15, S5 — 29 прогонов на
вариант.

## 4. Основной эксперимент: сравнение вариантов

> Предложение. Утверждается до обработки кампании r3.

### 4.1. Допуск

- **Серия** допускается, если в manifest: `finished` заполнено, `code.clean
  = true`, `parity.ok = true`, число прогонов каждой ячейки равно
  `settings.repeats`. Все серии одной платформы сняты на одном коммите кода.
- **Прогон** допущенной серии используется всегда (раздел 1.6).
- Серия, не прошедшая допуск, не используется целиком, и это указывается в
  разделе «Качество данных» отчёта.

### 4.2. Что сравниваем: отношение вариант / three.js

Каждый вариант R3F сравнивается с three.js той же платформы, того же
сценария и той же точки нагрузки. Эффект — **отношение средних
геометрических** метрики по прогонам:

```
R = exp( mean(ln x_вариант) − mean(ln x_three.js) )
```

R = 1,08 читается как «у варианта метрика на 8% больше, чем у three.js»
(для времени кадра и задержки — медленнее; для ёмкости — лучше).

Почему среднее геометрическое прогонов, а не медиана прогонов: медиана
по прогонам ведёт себя плохо в двухуровневых ячейках — так же, как медиана
кадров в Firefox (раздел 2.1): при долях уровней около половины она
«выбирает» один из уровней случайно. Среднее логарифмов учитывает все
прогоны и согласовано с расчётом числа прогонов (раздел 3), сделанным на
той же шкале.

### 4.3. Неопределённость: доверительный интервал

Для R строится **бутстреп-интервал** (10 000 повторов, фиксированное зерно):
прогоны варианта и прогоны three.js независимо выбираются с возвращением,
каждый раз пересчитывается R; интервал — перцентили полученных R.

- **95%-ный интервал** — для вывода о различии;
- **90%-ный интервал** — для вывода об эквивалентности (раздел 4.4).

Бутстреп не требует нормальности распределения метрики, что важно для
задержки и ёмкости.

### 4.4. Вывод по сравнению

Граница практической значимости — δ сценария (5% или 10%, раздел 3, шаг 5).
Эквивалентность проверяется тестом TOST: варианты «практически равны»,
если весь 90%-ный интервал R лежит внутри [1/(1+δ); 1+δ] — то есть
разница, если она есть, меньше порога.

Возможные выводы:

| Вывод | Условие | Как читать |
|---|---|---|
| **≈ равны** | 90%-ный интервал внутри границ, 95%-ный содержит 1 | разницы нет или она меньше порога |
| **≈ равны, разница X%** | 90%-ный интервал внутри границ, 95%-ный не содержит 1 | разница есть, но меньше порога — практически несущественна |
| **больше / меньше на X%** | 95%-ный интервал не содержит 1 и выходит за границу; после поправки Холма (4.5) значимо | существенная разница |
| **не ясно** | ни одно из условий | данных недостаточно для вывода |

### 4.5. Множественные сравнения

На одной платформе в одном сценарии проверяется несколько гипотез (в S2 —
4 варианта против three.js). Чем больше проверок, тем выше шанс случайно
получить «значимый» результат. Поэтому p-значения корректируются
**поправкой Холма** внутри семьи «сценарий × платформа» (в S1 — «сценарий ×
точка × платформа»).

p-значение для различия — **перестановочный тест** по разности средних
логарифмов: метки «вариант / three.js» случайно перемешиваются 10 000 раз, и
p — доля перемешиваний, где разница не меньше наблюдаемой. Тест, как и
бутстреп, не требует нормальности.

### 4.6. Двухуровневые ячейки

В каждой ячейке основной серии проверяется критерий двух уровней
(раздел 3, шаг 6; при n ≥ 30 — не меньше 3 прогонов в каждой группе). Для
двухуровневой ячейки отчёт даёт:

- положение каждого уровня (среднее геометрическое прогонов уровня);
- долю прогонов на каждом уровне с 95%-ным интервалом;
- общее R по разделу 4.2 с пометкой «двухуровневая» — интервал у него
  широкий, и вывод чаще всего «не ясно»; это честное отражение того, что
  разброс задаётся состоянием процесса, а не технологией.

### 4.7. Объяснение различий: фазы

Если вариант медленнее three.js, фазы показывают, где теряется время:

- **S1, S2** — средние логика / отрисовка на CPU / вне фаз / GPU по
  прогонам; разница фаз «вариант − three.js» в мс и в доле кадра;
- **S3** — этапы загрузки;
- **S4** — медианы фаз отклика.

Фазы описываются (медианы по прогонам и их разница), без отдельных
статистических тестов: они нужны, чтобы объяснить уже установленное
различие, а не искать новые.

### 4.8. WebKit (дополнительная серия)

В WebKit частоту кадров нельзя снять с ограничения 60 FPS: если кадр
готов быстрее 16,7 мс, он всё равно ждёт экрана. Поэтому:

- **S2** — главная метрика вместо времени кадра — **время работы CPU на
  кадр**: среднее (`update_ms` + `render_ms`). Время кадра приводится, но не
  сравнивается.
- **S3, S4** — как на других платформах; задержка S4 включает ожидание
  экрана — это то, что видит пользователь Safari.

### 4.9. Сравнение платформ

Отношения R одного и того же сравнения (например, «S2 · r3f-state /
three.js») на разных платформах приводятся рядом — таблицей и графиком.
Абсолютные миллисекунды разных платформ не сравниваются: машины и браузеры
разные, а для WebKit время кадра ограничено экраном. Отдельных тестов
«платформа A против платформы B» нет — это описательное сравнение.

### 4.10. Качество данных

Отдельный раздел отчёта, без влияния на выводы:

- допуск серий (4.1), число прогонов, сбои браузера (`retries`);
- **дрейф**: ранговая корреляция метрики с порядковым номером прогона в
  серии для каждой ячейки — не менялись ли условия за часы съёмки;
- S4: доля промахов по вариантам;
- S1, S2: доля кадров с измеренным GPU-временем;
- двухуровневые ячейки (4.6).

## 5. Открытые вопросы (решение за автором)

1. **Эффект — отношение средних геометрических (4.2).** Альтернатива —
   отношение медиан по прогонам; минус описан в 4.2.
2. **Интервалы — бутстреп, p-значения — перестановочный тест (4.3, 4.5).**
   Альтернатива — t-тест Уэлча на логарифмах: проще и даёт интервал и
   p-значение одной формулой, но предполагает нормальность.
3. **Метрика WebKit S2 — время CPU на кадр (4.8).**
4. **Неопределённая ёмкость S5** (порог не пересечён в пройденных
   уровнях). Предложение: такие прогоны помечаются («ёмкость < 100» или
   «> 51 200»), а сравнение ячейки ведётся по рангам (кто больше), без
   отношения R. В пилоте таких прогонов не было.
5. **Порядок выводов в 4.4** — устраивает ли формулировка «≈ равны,
   разница X%» для случая «разница статистически есть, но меньше порога».
